## Finding fixed

The scheduled Facebook/Instagram dispatcher already stopped automatic retries for transport failures and provider 5xx responses after a publish request began. However, a successful provider response with malformed JSON or no post ID, and a local database persistence error after the provider accepted the post, could still enter the normal retry path. That could create duplicate social posts.

The dispatcher now treats these post-request outcomes as ambiguous:
- transport failures and timeouts;
- provider 5xx responses;
- malformed response data;
- a response without a usable post ID;
- SQLAlchemy persistence failures after the publish request.

Explicit provider 4xx responses remain definitive rejections and are not classified as ambiguous. Ambiguous outcomes fail closed with the existing manual-verification warning instead of being retried automatically. This reduces duplicate risk; it does not provide exactly-once publishing or provider-side reconciliation.

A regression test covers malformed response/missing-ID and database-error classification.
